# Plano — Mapa de Riscos por Unidade e Setor

Documento de planejamento do módulo **Mapas de Riscos (PGR)** no SIGES React.
Nada foi implementado ainda: este arquivo descreve modelo de dados, telas,
serviços, permissões, offline, alertas, PDF e a ordem de execução.

---

## 1. Objetivo

Permitir que cada unidade mantenha, **por setor do organograma**, o seu mapa de
riscos com:

- **arquivo** anexado (PDF/imagem) da versão vigente;
- **inventário estruturado** de riscos (perigo, avaliação, controles, ações);
- **histórico de revisões** (cada revisão guarda seu próprio arquivo e inventário);
- **validade com alerta de vencimento**;
- **fluxo de aprovação** (rascunho → em aprovação → aprovado/reprovado);
- **exportação em PDF** gerada pelo próprio sistema;
- **consulta offline** dos dados já baixados.

### Fora do escopo desta primeira entrega

- Editor de planta/planta baixa com marcação gráfica de riscos.
- Integração com eSocial / S-2240.
- Assinatura digital certificada (apenas registro de quem aprovou e quando).
- Criação/edição **offline** (a fila de escrita offline fica para uma fase 2 —
  ver §8).

---

## 2. Decisões de arquitetura

| Tema | Decisão | Motivo |
|------|---------|--------|
| Granularidade | 1 mapa por **unidade + nó do organograma** (`cfg_units_assets_tags.id`), com `NULL` = "unidade inteira" | "Setores do organograma" são os nós de `cfg_units_assets_tags` (`getUnitStructureNodes`), não o agrupamento por `asset_tag_id` que a `UnitView` usa nos cards |
| Histórico | `risk_maps` (cabeçalho) + `risk_map_revisions` (snapshot por revisão) + `risk_map_items` (inventário da revisão) | Cada revisão é um retrato imutável: arquivo e inventário do que foi aprovado |
| Arquivo | R2 (`r2Service.uploadFile`) em `companies/{companyId}/risk-maps/{mapId}/rev-{n}/...` | Mesmo padrão de `technicals_manuals_files` |
| Aprovação | Status na revisão + `route_key` próprio `risk_maps_approve` (`can_edit` = pode aprovar) | Não exige coluna nova em `cfg_profiles_access` nem mudança no `PermissionsContext` |
| Vencimento | Calculado na leitura (`next_review_date`/`valid_until`) | Não há cron/back-end; o app calcula e destaca |
| Offline | Leitura pelo cache do `offlineLayer` (`OFFLINE_READ_METHODS`) | Custo baixo, mesmo mecanismo das outras telas |
| Exclusão | Soft delete (`is_deleted`) em `risk_maps` | Padrão do repo |
| Escopo por cliente | `units.clients_ids` filtrado no serviço (`normalizeClientScope`) + `useClientScope` na tela | Padrão das listas de unidades |

### Fluxo de status

```
risk_map_revisions.status

draft ──submit──> pending_approval ──approve──> approved
  ^                     │                          │
  └──────reject─────────┘                          │ (nova revisão aprovada)
                                                   v
                                              superseded
```

- `risk_maps.status` é o **resumo** do mapa (mantido por trigger):
  `draft` | `pending_approval` | `approved` | `rejected` | `expired` | `archived`.
- Só revisão `draft` pode ser editada/excluída.
- Ao aprovar uma revisão, a anterior aprovada vira `superseded`.
- `expired` é derivado de `next_review_date < CURRENT_DATE` — a view sempre
  devolve `days_to_expire`, então o app não depende do status gravado.

RETURNS text
    LANGUAGE sql IMMUTABLE PARALLEL SAFE
    AS $$
    SELECT CASE
        WHEN p_level IS NULL THEN NULL
        WHEN p_level <= 4  THEN 'baixo'
        WHEN p_level <= 9  THEN 'moderado'
        WHEN p_level <= 16 THEN 'alto'
        ELSE 'critico'
    END
$$;

### 3.3 Triggers de consistência

```sql
-- 3.3.1 Aprovação: só quem tem risk_maps_approve/edit; carimba autor e data.
CREATE OR REPLACE FUNCTION public.fc_risk_map_revision_guard()
RETURNS trigger
    LANGUAGE plpgsql SECURITY DEFINER
    SET search_path = public
    AS $$
DECLARE
    v_user_id bigint;
BEGIN
    v_user_id := (SELECT u.id FROM public.users u WHERE u.uuid = auth.uid());

    IF NEW.status = 'approved' AND COALESCE(OLD.status, '') <> 'approved' THEN
        IF NOT public.fc_has_route_permission('risk_maps_approve', 'edit') THEN
            RAISE EXCEPTION 'Usuário sem permissão para aprovar mapas de riscos'
                USING ERRCODE = '42501';
        END IF;
        NEW.approved_by_user_id := COALESCE(NEW.approved_by_user_id, v_user_id);
        NEW.approved_at := COALESCE(NEW.approved_at, timezone('America/Sao_Paulo', now()));
    ELSIF NEW.status <> 'approved' THEN
        NEW.approved_by_user_id := NULL;
        NEW.approved_at := NULL;
    END IF;

    IF NEW.status = 'pending_approval' AND COALESCE(OLD.status, '') <> 'pending_approval' THEN
        NEW.submitted_by_user_id := COALESCE(NEW.submitted_by_user_id, v_user_id);
        NEW.submitted_at := COALESCE(NEW.submitted_at, timezone('America/Sao_Paulo', now()));
    END IF;

    NEW.updated_at := timezone('America/Sao_Paulo', now());
    RETURN NEW;
END $$;

DROP TRIGGER IF EXISTS trg_risk_map_revisions_guard ON public.risk_map_revisions;
CREATE TRIGGER trg_risk_map_revisions_guard
    BEFORE INSERT OR UPDATE ON public.risk_map_revisions
    FOR EACH ROW EXECUTE FUNCTION public.fc_risk_map_revision_guard();
```

```sql
-- 3.3.2 Cabeçalho: reflete a revisão aprovada e a próxima revisão.
CREATE OR REPLACE FUNCTION public.fc_risk_map_sync_header()
RETURNS trigger
    LANGUAGE plpgsql SECURITY DEFINER
    SET search_path = public
    AS $$
DECLARE
    v_map_id       bigint := COALESCE(NEW.risk_map_id, OLD.risk_map_id);
    v_approved_id  bigint;
    v_approved_by  bigint;
    v_approved_at  timestamp without time zone;
    v_next_review  date;
    v_status       character varying(20);
BEGIN
    -- Nova revisão aprovada: as anteriores viram 'superseded'
    IF NEW.status = 'approved' THEN
        UPDATE public.risk_map_revisions
           SET status = 'superseded'
         WHERE risk_map_id = v_map_id
           AND id <> NEW.id
           AND status = 'approved';
    END IF;

    SELECT r.id,
           r.approved_by_user_id,
           r.approved_at,
           COALESCE(r.valid_until,
                    (r.revision_date + make_interval(months => m.review_interval_months))::date)
      INTO v_approved_id, v_approved_by, v_approved_at, v_next_review
      FROM public.risk_maps m
      LEFT JOIN public.risk_map_revisions r
             ON r.risk_map_id = m.id AND r.status = 'approved'
     WHERE m.id = v_map_id
     ORDER BY r.revision_number DESC
     LIMIT 1;

    IF v_approved_id IS NULL THEN
        v_next_review := NULL;
        IF EXISTS (SELECT 1 FROM public.risk_map_revisions
                    WHERE risk_map_id = v_map_id AND status = 'rejected') THEN
            v_status := 'rejected';
        ELSIF EXISTS (SELECT 1 FROM public.risk_map_revisions
                       WHERE risk_map_id = v_map_id AND status = 'pending_approval') THEN
            v_status := 'pending_approval';
        ELSE
            v_status := 'draft';
        END IF;
    ELSIF v_next_review IS NOT NULL AND v_next_review < CURRENT_DATE THEN
        v_status := 'expired';
    ELSE
        v_status := 'approved';
    END IF;

    UPDATE public.risk_maps
       SET approved_revision_id = v_approved_id,
           approved_by_user_id  = v_approved_by,
           approved_at          = v_approved_at,
           next_review_date     = v_next_review,
           status               = v_status,
           updated_at           = timezone('America/Sao_Paulo', now())
     WHERE id = v_map_id;

    RETURN NULL;
END $$;

DROP TRIGGER IF EXISTS trg_risk_map_sync_header ON public.risk_map_revisions;
CREATE TRIGGER trg_risk_map_sync_header
    AFTER INSERT OR UPDATE OR DELETE ON public.risk_map_revisions
    FOR EACH ROW EXECUTE FUNCTION public.fc_risk_map_sync_header();
```

> Observação: o trigger é `SECURITY DEFINER` porque precisa atualizar
> `risk_maps` mesmo quando quem aprovou não tem `can_edit` no mapa.

RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
DECLARE
    v_table text;
BEGIN
    FOREACH v_table IN ARRAY ARRAY['risk_maps','risk_map_revisions','risk_map_items'] LOOP

             WHERE tr.tgrelid = to_regclass('public.' || v_table)

               AND NOT tr.tgisinternal

            EXECUTE format(

                'trg_audit_' || v_table, v_table
            );
        END IF;
    END LOOP;
END $$;

Detalhes de implementação:

- `createRiskMap` cria o mapa **e** a revisão 1 na sequência; se a revisão
  falhar, desfaz o mapa (soft delete) para não deixar cabeçalho órfão.
- `saveRiskMapItems`: `upsert` com `onConflict: 'id'` para itens existentes,
  `delete().in('id', removidos)` para os que saíram da tela, e
  `insert` para os novos. `item_number` = posição na lista.
- Upload usa `r2Service.uploadFile` em
  `companies/{companyId}/risk-maps/{riskMapId}/rev-{n}/{Date.now()}.{ext}`
  e grava `doc_file_path/name/type/size` na revisão.
- `doc_file_type` inferido do `file.type` (mesma lógica do
  `technicalManualsService.uploadTechnicalManualFile`).

## 8. Offline — o que funciona e o que não

| Cenário | MVP |
|---------|-----|
| Abrir a aba da unidade offline | Sim, se já abriu online (cache do `offlineLayer`) |
| Ver inventário e histórico offline | Sim (métodos em `OFFLINE_READ_METHODS`) |
| Abrir o PDF/imagem do R2 offline | **Não garantido** — depende do cache do WebView. Botão "Baixar para o aparelho" salva via `r2Service.downloadFile` + `FileUtils` (arquivo fica no dispositivo, mas não é reaberto pelo app) |
| Criar/editar mapa ou inventário offline | **Não** nesta fase (fila de escrita exige `OFFLINE_OPS` por método) |

Recomendação: comunicar isso na UI com um aviso discreto quando offline
("Dados salvos no aparelho. Edição exige conexão.").
